一什么是 DDD

DDD 是 Eric Evans 在 2003 年提出的一套软件设计方法论，核心思想是：软件的复杂度应该来自业务领域本身，而不是技术实现。设计软件时以业务领域为中心，让代码反映真实的业务模型。

二核心概念

领域Domain

软件要解决的业务问题空间。比如电商领域的「下单、支付、库存」。

领域模型Domain Model

对业务概念的抽象表示。不是数据库表结构，而是业务语言中的实体和规则。

统一语言Ubiquitous Language

开发者和业务人员使用同一套术语沟通。代码里的类名、方法名直接用业务术语。

限界上下文Bounded Context

同一个词在不同业务模块里含义不同，划清边界，每个上下文有自己独立的模型。

反面 — 技术语言

dao.updateStatus(orderId, 3);

正面 — 业务语言

order.pay();

三战术模式（代码层面）

概念说明代码形态
聚合根 Aggregate Root聚合的入口，负责维护内部一致性实体类，如 class Order
实体 Entity有唯一标识，生命周期可追踪类，如 class OrderItem
值对象 Value Object没有唯一标识，靠属性值判断相等，不可变不可变类，如 class Money
领域事件 Domain Event表示领域中发生的有意义的事情类，如 class OrderSubmittedEvent
仓储 Repository模拟集合的持久化接口，只暴露聚合根的存取接口，如 interface OrderRepository
领域服务 Domain Service不属于任何实体的业务逻辑类，如 class TransferService
枚举 Enum有限状态集合枚举，如 enum OrderState

四分层架构

用户界面层UI / API接收请求，返回响应
应用层Application编排流程，不含业务规则
领域层Domain核心业务逻辑，不依赖外部
基础设施层Infrastructure数据库、消息队列、外部 API
领域层不依赖任何外层。数据库、框架都是可替换的，业务规则才是核心。

五聚合与聚合根

5.1 概念 vs 类

术语本质
聚合 Aggregate概念，逻辑分组，没有对应的 class
聚合根 Aggregate Root代码，具体的类，如 class Order

聚合是整个家族，聚合根是族长。

Order 聚合

Order 聚合根 · 族长
OrderItem 实体
OrderItem 实体
ShippingAddress 值对象
OrderMoney 值对象
OrderState 枚举

5.2 聚合内部 vs 聚合之间

聚合内部 — 直接调用，事务一致

order.addItem(coffee, 2);

聚合之间 — 通过领域事件解耦

OrderSubmittedEvent event = order.submit();

// CouponService 听到事件 → 标记优惠券已使用
// InventoryService 听到事件 → 扣减库存

5.3 一个领域模型可以有多个聚合

order/                          ← 订单领域的领域模型
├── Order.java                  ← 聚合根（聚合 1：订单）
│   ├── OrderItem.java          ← 聚合内部实体
│   └── OrderMoney.java         ← 值对象
│
├── ShoppingCart.java           ← 聚合根（聚合 2：购物车）
│   └── CartItem.java           ← 聚合内部实体
│
└── Coupon.java                 ← 聚合根（聚合 3：优惠券）
    └── CouponRule.java         ← 值对象

聚合之间通过 ID 引用，不直接持有对方：

// Order 引用 Coupon，但不持有 Coupon 对象
private CouponId appliedCouponId;  // 值对象，只是个标识

5.4 聚合边界怎么画

问题答案指向
这两个对象必须在同一个事务中修改吗？是 → 同一个聚合
这个对象离开另一个对象能独立存在吗？能 → 不同聚合
这个对象是被整体替换还是独立生命周期？整体替换 → 值对象；独立生命 → 另一个聚合的引用

5.5 持久化也体现聚合根的门卫角色

// 只有聚合根有仓储，没有 OrderItemRepository
public interface OrderRepository {
    Order findById(OrderId id);      // 查出来是整个聚合
    void save(Order order);          // 存进去也是整个聚合
}

六限界上下文

6.1 核心思想

同一件事，在不同场景下长不同的样子。现实中「商品」的例子：

场景关注什么不关心什么
仓库管理员库位、重量、长宽高价格、评价
销售价格、折扣、促销库位、重量
客服退换货政策、保修期库位、价格
物流体积、重量、是否易碎价格、评价

6.2 代码层面：同一杯「咖啡」的三种样子

菜单上下文 Menu

public class Coffee {
    private String name;
    private Money price;
    private String description;
}

库存上下文 Inventory

public class CoffeeStock {
    private String coffeeName;
    private int quantity;
    private String warehouseLocation;
}

订单上下文 Order

public class CoffeeLineItem {
    private String coffeeName;
    private int quantity;
    private Money subtotal;
}

它们之间通过名字或 ID 关联，而不是共享一个类。

6.3 为什么不能用一个类

// 大一统模型 — 反面教材
public class Coffee {
    private String name;
    private Money price;
    private String description;      // 菜单需要
    private int stock;               // 库存需要
    private String warehouse;        // 库存需要
    private String returnPolicy;     // 客服需要
    private double weight;           // 物流需要
    private double volume;           // 物流需要
    private List<Review> reviews;    // 营销需要
}
  • 菜单团队改了 name，订单团队的逻辑可能挂掉
  • 库存团队加个字段，要等所有团队都同意
  • 一个类十几个字段，没人知道哪些跟自己有关

6.4 上下文之间的映射关系

模式含义
共享内核 Shared Kernel两个上下文共享一小部分模型
客户-供应商 Customer-Supplier上游提供数据，下游消费
防腐层 Anti-Corruption Layer下游建一层适配器，隔离上游模型
开放主机服务 Open Host Service上游提供标准 API 供多个下游调用

七完整领域模型代码示例

order/
├── Order.java                 ← 聚合根
├── OrderId.java               ← 值对象（标识）
├── OrderItem.java             ← 实体（聚合内部）
├── OrderState.java            ← 枚举（状态机）
├── OrderMoney.java            ← 值对象（金额计算）
├── OrderSubmittedEvent.java   ← 领域事件
├── OrderRepository.java       ← 仓储接口
└── OrderService.java          ← 领域服务

聚合根

public class Order {
    private OrderId id;
    private String customer;
    private List<OrderItem> items = new ArrayList<>();
    private OrderState state = OrderState.DRAFT;
    private OrderMoney total;

    public void addItem(Coffee coffee, int quantity) {
        if (state != OrderState.DRAFT) {
            throw new IllegalStateException("已提交的订单不能修改");
        }
        items.add(new OrderItem(coffee, quantity));
        recalculateTotal();
    }

    public OrderSubmittedEvent submit() {
        if (items.isEmpty()) {
            throw new IllegalStateException("空订单不能提交");
        }
        this.state = OrderState.SUBMITTED;
        return new OrderSubmittedEvent(this.id, this.customer, this.total);
    }

    private void recalculateTotal() {
        this.total = items.stream()
            .map(OrderItem::subtotal)
            .reduce(OrderMoney.ZERO, OrderMoney::add);
    }
}

值对象

public class OrderMoney {
    private final BigDecimal amount;
    private final Currency currency;

    public OrderMoney multiply(int factor) {
        return new OrderMoney(amount.multiply(BigDecimal.valueOf(factor)), currency);
    }

    public OrderMoney add(OrderMoney other) {
        assertSameCurrency(other);
        return new OrderMoney(amount.add(other.amount), currency);
    }
}

领域事件

public class OrderSubmittedEvent {
    private final OrderId orderId;
    private final String customer;

领域服务

public class OrderService {
    private final OrderRepository repository;
    private final InventoryService inventory;

    public Order createOrder(String customer, List<OrderRequest> requests) {
        Order order = new Order(customer);
        for (OrderRequest req : requests) {
            Coffee coffee = inventory.findCoffee(req.getCoffeeName());
            if (!inventory.isAvailable(coffee, req.getQuantity())) {
                throw new OutOfStockException(coffee.getName());
            }
            order.addItem(coffee, req.getQuantity());
        }
        return order;
    }
}

八各类的职责边界

类型有 ID可变职责
聚合根 Order有是维护内部一致性，暴露行为
实体 OrderItem有是聚合内部的对象，通过聚合根访问
值对象 OrderMoney、OrderId无不可变描述属性，靠值判等
枚举 OrderState无不可变有限状态集合
领域事件 OrderSubmittedEvent无不可变记录发生了什么
仓储接口 OrderRepository——持久化抽象，实现放在基础设施层
领域服务 OrderService——跨实体、跨聚合的业务逻辑

九什么时候用 DDD

适合

  • 业务逻辑复杂（金融、电商、物流）
  • 团队规模较大，需要统一语言
  • 长期维护的核心系统

不适合

  • 简单 CRUD 应用
  • 小型项目、原型
  • 一次性脚本或短期项目

十总结

概念管「怎么想」，类管「怎么写」聚合、领域模型、限界上下文是脑中的画布；聚合根、实体、值对象是画布上的笔触。
领域模型是一个团队，不是一个人聚合根是队长，值对象是工具，实体是队员，事件是传话筒。
聚合是房子，聚合根是门所有人只能从门进出，内部秩序由门卫保证。
限界上下文就是给不同场景画墙同一个业务概念在不同场景下含义不同，就应该有各自的模型，各自独立演进。
DDD 不是技术框架，而是一种思维方式让代码忠实地反映业务，而不是让业务去迁就技术。
